# 发票识别：有没有更优方案？

> 出具日期：2026-09-11 · 背景：P9 修完外部 OCR 缺陷（坐标锚定，34/72 → 64/72）后，评估是否还有更优路线。
> 结论一句话：**瓶颈从来不是 OCR 引擎的精度，而是数据源。真正的更优方案是换源（税局权威数据）+ 支持 XML，而不是换 OCR 库。**

---

## ⚠️ 边界声明（先读这条，防误读）

**本系统 / 本 agent 无法、也不会以任何程序化方式连接税务局。** 全文出现的「换数据源」「方案 A」指的都是**人工导出**，不是自动拉取：

| | 实际情况 |
|---|---|
| ❌ 系统直连税局取数 | **不可能**。税法上唯一合法的程序化通道是**乐企（Natural System）**，门槛：上年度营收 ≥5000 万、开票+受票量 ≥1 万份（多地口径 5 万份）或开票金额 ≥1 亿、纳税信用 **A/B 级**、自有系统**软件著作权** + **固定 IP** + **等保 2.0** 备案、省级税务机关审批。**高迥（杭州）贸易为小微企业，全部不满足。** |
| ❌ 第三方爬税局 / 模拟登录 | **不做**。违反《发票管理办法》与网络安全相关规定，风险不可控。 |
| ✅ 唯一现实路径 | **哥哥手动登录电子税务局** → 税务数字账户 → 全量发票查询 → 导出 Excel / 批量下载 XML·OFD → 丢进 `work/`。**系统只负责：拿到文件后解析、归档、对账。** |

**一句话**：手动导出是人的动作，解析归档是系统的动作。这条线不能混。

---

## 0. TL;DR — 四个方案，按价值排序

| # | 方案 | 性质 | 收益 | 成本 | 建议 |
|---|---|---|---|---|---|
| **A** | **换数据源：哥哥手动导出税局「全量发票查询」Excel / 批量下载 XML**（⚠️ **人工操作，非自动**） | 取数路线 | ⭐⭐⭐⭐⭐ 识别误差归零 + 拿到法定归档件 | 哥哥手动几十秒 + 一次性对账脚本（我写） | **首选，先做**（待哥哥导出） |
| **B** | **支持 XML / OFD 附件** | 🔴 **合规刚需** | ⭐⭐⭐⭐ 结构化零误差 + 可验签 + 补上法定归档格式 | 小（parser 几十行） | ✅ **已交付（2026-09-11，见 §3.4）** |
| **C** | PaddleOCR → RapidOCR | 工程优化 | ⭐ 瘦身 ~2GB、CPU 快 4× | 极小（1 个函数） | 可做，但**优先级最低** |
| **D** | 税局数据 ↔ 邮箱附件**双向交叉校验** | 质量兜底 | ⭐⭐⭐⭐ 漏票 / 多票 / 金额不符全查得出 | 中 | A 做完紧接着做 |

**一句话决策**：A + B 是正解，C 是锦上添花，D 是 A 的必然搭配。

## 1. 先看事实：现状实测（不猜，都是跑出来的）

### 1.1 PaddleOCR 在我们的工作负载上「几乎从不运行」

翻 2026-09-11 全量补收的产物（`logs/backfill_history_invoices_20260911-020234.json` + `logs/ocr_audit_20260911-013834.json`）：

| 事实 | 数值 |
|---|---|
| 候选邮件 | 66 封（带附件 50 / 无附件 16） |
| 去重后附件总数 | **110 个** |
| 扩展名分布 | **PDF 109 + PNG 1** |
| 有文本层的 PDF | **109 / 109（100%）** |
| 文本层为空、真正需要转图 OCR 的 PDF | **0** |

机制上：`process_pdf()` 的 OCR 兜底**只在文本层为空时触发**（`ocr_invoice.py:423` `if not blob:`）。
**109 个 PDF 文本层全部非空 → PaddleOCR 在 PDF 路径上从未真正执行**，唯一可能走图片 OCR 的是那 **1 个 PNG**（还是个非发票件）。

> ⚠️ 顺带纠正一个早前的误读：修复前 audit 里出现过 `source: ocr` **44 行**，看起来像"44 个文件跑了 OCR 且失败"。实际不是 —— 那是旧 `_source` 判定（`"发票号码" in blob`）把**有文本层但非发票**的行程单/结算单**误标**成了 `ocr`。P9 已改成「按文本层是否为空」判定，属于**可观测性 bug**，不是真的跑了 44 次 OCR。这条误标正是当初误判"有 7 个扫描件"的源头。

### 1.2 修复后的真实水平（109 个真实附件回归）

| 指标 | 结果 |
|---|---|
| 发票类可识别 | 34/72（47%）→ **64/72** |
| 真发票通过率 | **64/64 = 100%** |
| 买卖方税号互换 | **0** |
| 大写金额交叉校验 | **64/64 一致** |
| 旧版能过的 17 张 | **零回归** |

**结论：纯 PDF 场景下，我们已到 100%。继续调 OCR 引擎，边际收益 ≈ 0。**

## 2. 方案 A（首选）：换数据源 —— 电子税务局「全量发票查询」

### 2.1 为什么这是最优解

我们现在做的是：**发件人给什么 PDF → 从 PDF 里猜字段**。
税务局的税务数字账户里，**本企业取得的全部发票本来就有一份权威记录**。直接取那份，识别误差这个概念就不存在了。

### 2.2 具体路径（两个产出，都拿到）

> 登录电子税务局 → **我要办税** → **税务数字账户** → **发票查询统计** → **全量发票查询**
> → 查询类型选 **「取得发票」** → 设查询条件（建议按期/按年）

| 产出 | 操作 | 用途 |
|---|---|---|
| ① **Excel 明细** | 左上角 **【导出】** → 导出全部（含**发票基础信息 + 货物清单 + 信息汇总表**） | **当权威真值对账**（见方案 D） |
| ② **XML / OFD / PDF** | 勾选数据 → **【批量下载】** → 选文件下载类型 → 确认（进度看【批量导入导出进度查询】） | **法定归档件**（见方案 B） |

### 2.3 从"猜"到"取"的收益

- **零识别误差**：字段来自税局原始数据，不是从排版里反推
- **有明细行**：货物/服务清单（品名、规格、数量、单价、税率）——这是 PDF 正则**做不到**的
- **天然防重复报销**：税局侧每张票唯一，可做重复检测基准
- **覆盖"点链接下载"型邮件**：本次有 **16 封主题命中但无附件**的邮件被跳过了，税局侧直接补齐

### 2.4 必须说清的限制 ⚠️

| 限制 | 影响 | 应对 |
|---|---|---|
| 文件（OFD/XML）批量下载**只对数电票有效**，公告明确"不支持直接对于其他税控平台开具的发票进行下载" | 2023 年的老式同程/滴滴票**下不到 XML** | 老票继续用 PDF 文本层（我们已 100% 可读） |
| 但 **Excel 导出覆盖全部取得发票**（含老式） | — | 老票的**对账真值**仍可从 Excel 拿 |
| 只能查到**已上传**的发票 | 极新开的票可能有延迟 | 邮箱链路保留为"实时通道" |
| 月初平台卡顿 | 批量下载可能排队 | 分批 + 避开月初（税局自己这么建议） |

### 2.5 定位调整（关键）

```
现在：邮箱 PDF  ──OCR猜──▶  台账          （识别质量 = 瓶颈）
改后：税局数据  ──直接取──▶  台账（真值）  （无瓶颈）
      邮箱 PDF  ──────────▶  附件归档（留痕，法律需要原始凭证）
```

**邮箱链路的职责从「取数」降级为「归集附件」** —— 这是本方案最大价值。

## 3. 方案 B（合规刚需）：支持 XML / OFD

### 3.1 现状有个真缺口 🔴

`modules/mail_processor.py:66` 与 `tools/backfill_history_invoices.py:146` 的白名单都是：

```python
{".pdf", ".jpg", ".jpeg", ".png"}
```

**XML / OFD 附件会被直接跳过，且无日志、无提示、无计数** —— 静默丢弃。
（本次 110 个附件里恰好没有 XML/OFD，所以**目前没有实际损失**，但这是一颗埋着的雷：一旦有发件方改发 XML，我们会**毫无察觉地漏票**。）

### 3.2 合规依据（这是"必须"而不是"可选"的原因）

**财政部 / 国家档案局官方口径**（多地税务局答复口径一致）：

> 数电票提供 PDF、OFD 和 XML 三种电子文件格式。其中，**PDF 和 OFD 为预览发票内容的格式，含有数字签名的 XML 格式才是符合财政部入账要求的电子文件格式**。

依据文件：
- **财会〔2020〕6号**《关于规范电子会计凭证报销入账归档的通知》
  - 第三条：仅用电子件报销入账归档需满足「准确、完整、有效接收和读取电子会计凭证**及其元数据**」「**能有效防止电子会计凭证重复入账**」
  - 第四条：**以纸质打印件作为报销入账归档依据的，必须同时保存打印该纸质件的电子会计凭证**
- **财政部国家档案局令第79号**《会计档案管理办法》
- **财会便函〔2023〕18号**《电子凭证会计数据标准（试行版）》

➡️ 我们目前只归档 **PDF（预览件）**，对数电票而言**不满足"必须保存的电子会计凭证"要求**。

### 3.3 技术上还更简单

数电票 XML 是**结构化元数据**，字段直接可读，无需任何排版推理：

| 字段 | 说明 |
|---|---|
| 发票号码 / 开票日期 | 直接取 |
| 购买方 / 销售方 名称 + 统一社会信用代码 | 直接取（**不会再出现买卖方互换**） |
| 金额（不含税）/ 税额 / 价税合计 / 税率 | 直接取 |
| **明细行** | 品名、规格、数量、单价、金额、税率 —— PDF 拿不到 |
| 数字签名 | 可验签，满足"篡改可发现" |

成本预估：**一个 XML parser 几十行 + 白名单加 2 个扩展名 + 归档时保留原文件**。风险低（新增分支，不改 PDF 路径）。

### 3.4 ✅ 已交付（2026-09-11）

**新增** `modules/einvoice.py`（零第三方依赖，仅 stdlib）：

| 能力 | 实现 |
|---|---|
| 白名单单一事实来源 | `IMAGE_EXTS`（走 OCR）/ `EINVOICE_EXTS`（走结构化）/ `SUPPORTED_EXTS`（并集），模块内含 `assert` 防漂移。邮件同步、回填、重试三条链路统一引用，终结「三处手工同步」 |
| XML 解析 | `parse_einvoice_xml()`；兼容**命名空间**、**元素大小写变体**（`Einvoice`/`TotaltaxIncludedAmount`）、**多版本别名**；按**父节点消歧**（明细行的 `TotaltaxIncludedAmount` 不会串到顶层价税合计） |
| 明细行 | `明细行` 列表（品名/规格/单位/数量/单价/金额/税率/税额），PDF 正则拿不到 |
| 金额归一 | 税额 6 位小数（`0.120000`）→ 2 位；分位各自取整后若 `不含税+税额 ≠ 价税合计`，**丢弃不含税金额让下游按「价税合计−税额」推导**并记 WARNING，而不是整张票被拒 |
| OFD | `extract_ofd_invoice_xml()` 在 ZIP 内找内嵌数电票 XML；找到则同源解析，找不到**明确报错**（提示去税局批量下载 XML），并对内嵌 XML 设 8MB 上限防解压炸弹 |
| 不静默丢弃 | 任何解析失败 → 附件落盘 `invoices/failed/` + WARNING 日志 + 可读原因（**这是本次修的核心缺陷**） |
| 归档 | XML/OFD 原件按开票月份归档进 `invoices/archive/<YYYY-MM>/`，`file_path` 落地 |
| 来源可审计 | `invoice_doc.ocr_version` 记为 `einvoice-xml` / `einvoice-ofd-xml`，与 OCR 来源可区分 |
| 补收预筛 | `tools/invoice_ocr_probe.probe_bytes()` 对 XML/OFD 走本地解析，**不启动 OCR 子进程** |

**改动清单**：`modules/einvoice.py`（新）、`modules/mail_processor.py`、`modules/mail_service.py`、
`tools/invoice_ocr_probe.py`、`财务系统.spec`（hiddenimports）、
生产 `config/settings.json`（两个邮箱白名单各加 `.xml/.ofd`，已备份）。

**验证**：新增回归 `tests/test_einvoice_xml.py` **24 例**；全量 **229 passed**（原 205 + 24）。
另做**脱离 pytest 的真实端到端**：XML 入库（¥600.00，税额 `33.960000`→`33.96`）、
OFD 内嵌 XML 入库（来源 `einvoice-ofd-xml`）、坏 XML → 明确报错 + 落盘留痕，
三条路径均在隔离 `FINANCE_SYSTEM_HOME` 下跑通并直接查库复核。

**遗留**：`release/财务系统.exe` 是 PyInstaller 打包产物，**源码改动需重新构建才生效**。

## 4. 方案 C（锦上添花）：PaddleOCR → RapidOCR

### 4.1 对比（多来源实测汇总）

| 维度 | PaddleOCR（现用） | RapidOCR（候选） |
|---|---|---|
| 推理后端 | PaddlePaddle 框架 | **ONNXRuntime**（免装 Paddle） |
| 安装体积 | **~2GB+** | **~50–200MB** |
| CPU 速度 | 4–5 秒/张 | **~1 秒/张（快 3–4×）** |
| 峰值内存 | ~1.2 GB | ~350 MB |
| 初始化 | 3–5 秒 | 1–2 秒 |
| 中文精度 | ≈98–99%（最准） | ≈93–99.5%（略低，实测报道有分歧） |
| 模型来源 | — | 就是 **PaddleOCR 官方模型转 ONNX** |
| 许可 | Apache 2.0 | Apache 2.0 |

接入极简（就是现在 `ocr_image()` 那一个函数的薄封装）：

```python
from rapidocr_onnxruntime import RapidOCR
engine = RapidOCR()
result, _ = engine("invoice.png")   # [[box, text, conf], ...]
```

### 4.2 但 —— 优先级最低

**实测 PaddleOCR 在我们的负载里几乎从不触发**（见 §1.1：109 个 PDF 全有文本层，只有 1 个 PNG）。
所以这不是"精度优化"，是"**减依赖**"：省 ~2GB 磁盘、加快冷启动、万一遇到扫描件/截图时快 4 倍。

➡️ **做了不亏，但不着急。** 建议等 A/B 落地后顺手做，顺便把 `ocr_image()` 的双后端（优先 RapidOCR、缺失则回退 PaddleOCR）做成可切换，零风险迁移。

### 4.3 其它候选（本次评估后**不推荐**）

| 方案 | 为什么不选 |
|---|---|
| EasyOCR | 拉 1.5GB PyTorch，2024 年后基本停更，中文数字混淆多 |
| Tesseract | 中文精度上限 ~90%，不够 |
| Surya | 版面理解强，但重（PyTorch）、偏英文文档 |
| **视觉大模型**（GPT/Qwen-VL 等） | 强，但**要联网、要花钱、发票数据外传有隐私问题** —— 对财务票据不合适；且我们现在根本不需要 OCR |

## 5. 方案 D：双向交叉校验（A 的必然搭配）

A 做起来之后，**顺手就能得到一个质量门禁**：

```
税局 Excel（真值集合）  ──┐
                          ├──▶ 比对 ──▶ ① 漏票（税局有、台账无）
邮箱 PDF（附件集合）    ──┘           ② 多票（台账有、税局无 → 可能是假票/未上传）
                                      ③ 金额/税额/日期不符
                                      ④ 重复入账
```

这比继续调 OCR 有用得多：**它检的是"该收的票收全了没"，而不是"这张票的数字猜对了没"。**
本次 63 张台账能不能覆盖 2023-11 ~ 2026-09 的全部进项，只有对账才知道。
